Colocated Prefill Progress Benchmark

混部 Prefill 压力场景：Progress 性能对照

进度：20/20 轮完成。 每个并发每组只运行一次，以下是本次实测，不代表统计稳定性。

4 张 B300、4 个 TP1 混部 worker；Qwen3-4B-Instruct-2507 BF16，128 GiB KV/worker。每轮回放预先筛选的 AgentX 快照：128 session，每个 session 的前 4 个模型请求，共 512 请求；同一并发的五组请求和 token 完全一致。保留原始 hash 的块共享结构，AgentInfer 重建模型 token ID；这不等于原始文本。同一 agent 的间隔压缩为 0，每 session 最多 1 个请求在途，原始重叠请求会被串行化。不同并发的合成 token ID 可能不同。其他 GPU 可能有任务，主机共享资源没有完全隔离。

这是一份有意筛选的 prefill 压力子集：候选 session 的 4 次请求输出合计不超过 2,048 token，按历史前缀估计的新增输入不少于 32,768 token；从符合条件的 217 个 session 中按输出总量由短到长选取 128 个。源请求长度和哈希块未修改；该结果反映目标场景，不代表全部 AgentX 流量。

按同 session、同模型较早输入快照计算，共同前缀占输入 token 的 62.60%。该值没有考虑 worker 分配、重叠、缓存淘汰和输出 KV，不是实际命中率。

策略：Cache = cache-aware；KV = kv-aware；P = progress；A = session affinity；Full = KV+A+P。两种 Progress 对照分别固定 A 关闭和开启。同一会话及 agent 的有效 affinity 绑定会优先复用 worker，因此已经命中绑定的选择不会重新按 progress 成本排序。

2. 端到端性能

吞吐是逻辑 token / 回放总时长，输入包含复用的 token；总吞吐 = 输入 + 输出。TTFT 和 TPOT 为每请求统计；TPOT = (请求时延 − TTFT) / (输出 token − 1)，仅统计输出大于一个 token 的请求。JCT 是 session 的 replay task duration，未执行真实工具调用；每轮有 128 个 session。

如何理解异常

单轮结果只能说明同步观察到的变化。若吞吐、命中、排队或时延方向不一致，先对照本地计算量、worker 分配、prefill/decode 时延和共享主机活动；没有直接证据时，不能把相关变化写成已证实的因果关系。报告记录每轮原始数据，便于进一步定位。
